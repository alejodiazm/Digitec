# Workflow: /a11y — Auditoría de Accesibilidad

## Contexto obligatorio
Leer `.agents/skills/accessibility.md` antes de ejecutar.

## Fase 1: Análisis Automático con axe

1. Navegar con el browser subagent a `http://localhost:3000`
2. Ejecutar auditoría automática desde DevTools:
   - Abrir Chrome DevTools → Lighthouse → Accessibility
   - Registrar el score inicial

## Fase 2: Revisión Manual de Contraste

Para cada combinación de texto/fondo, verificar en `contrast.ratio.fyi`:

```
Secciones claras (#F8FAFC, #F1F5F9):
□ Texto primario (#1E293B): ¿ratio ≥ 4.5:1?  → debe ser ~12:1
□ Texto secundario (#475569): ¿ratio ≥ 4.5:1? → debe ser ~6:1
□ Texto muted (#94A3B8): ¿ratio ≥ 3:1?       → SOLO para texto grande

Secciones oscuras (#0B1121, #0F172A):
□ Texto blanco (#FFFFFF): ¿ratio ≥ 4.5:1?    → debe ser ~18:1
□ Texto slate-300 (#CBD5E1): ¿ratio ≥ 4.5:1? → debe ser ~10:1
□ ❌ slate-500 (#64748B) sobre oscuro: FALLA — corregir si existe
```

## Fase 3: Estructura Semántica

3. Revisar en código:
```
□ ¿Exactamente 1 <h1> en page.tsx? (en Hero)
□ ¿Jerarquía H1 → H2 → H3 sin saltos?
□ ¿Todas las <section> tienen id de ancla?
□ ¿<nav>, <main>, <header>, <footer> presentes?
□ ¿Formulario tiene <label> asociados con htmlFor + id?
```

## Fase 4: Imágenes y ARIA

4. Buscar en todos los componentes:
```bash
grep -r "<img\|<NextImage" src/components --include="*.tsx"
```

Para cada imagen verificar:
- ¿Tiene `alt`?
- ¿El `alt` es descriptivo (no "image" o "foto")?
- ¿Las decorativas tienen `alt=""` + `aria-hidden="true"`?

5. Verificar botones icon-only:
```bash
grep -r "aria-label" src/components --include="*.tsx"
```
Cada botón que NO tiene texto visible debe tener `aria-label`.

## Fase 5: Navegación por Teclado

6. Con el browser subagent, navegar SOLO con Tab:
- ¿Todos los elementos interactivos son alcanzables?
- ¿El focus es visible (no invisible)?
- ¿El menú mobile abre y cierra con Enter/Escape?
- ¿El formulario es completable con teclado?
